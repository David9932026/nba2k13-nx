## 1. 整体形状

```

        │  照常调用 D3D9 API，照常把命令写进 PM4 环
        ▼
  ┌──────────────────────────────┐
  │  rexglue-sdk（打了本仓库补丁）│
  │  ├ 内核层：xboxkrnl / xam     │
  │  ├ 图形层：命令处理器 + 环    │
  │  └ 平台层：Switch / Win32     │
  └───────┬───────────────┬──────┘
          │               │
   模拟 Xenos 路径     原生路径（本项目）
   （保留，可回退）    （默认）
          │               │
          ▼               ▼
   Vulkan（nvk/mesa）  Vulkan 直接录绘制
```

两条路并存，靠 `NBA2K13_renderizador = "nativo"` 切换。模拟路径一直留着当对照 ——
这是排查"到底是我的原生渲染器的问题，还是游戏/内核层的问题"的唯一干净基线。

## 2. PM4 命令环

游戏的 D3D 不直接调驱动，而是把命令写进一个**环形缓冲区**，再从另一头读出来执行。
原生渲染器**不拦截 D3D 调用**，只读这个环 —— 因为环上已经是"最终要被 GPU 执行的东西"。

- 环位置：`01F20000`，**1,048,576 个 32 位字**（4 MB）
- 中断回调：`82CAD970`
- 包类型（本项目实测常见的）：

| opcode | 名称 | 用途 |
|---|---|---|
| `0x36` | `PM4_DRAW_INDX_2` | 绘制 |
| `0x37` | `PM4_INDIRECT_BUFFER_PFD` | 间接缓冲（预取） |
| `0x3c` | `PM4_WAIT_REG_MEM` | 等某个寄存器变成某个值（握手，不做会卡死） |
| `0x3f` | `PM4_INDIRECT_BUFFER` | 间接缓冲 |
| `0x27` | `PM4_IM_LOAD` | 加载着色器指令内存 |

环读不动时会表现为"GPU 利用率 0、CPU 满"—— 不是 GPU 被锁死，是**没有命令喂进去**，
CPU 在原地空转（见修复账本 C43/C44）。

## 3. 原生渲染器骨架

移植自 nfsmw-nx 的原生渲染器（GPL-3.0），2K13 侧的实现在 `app/src/nativo/`。

### 3.1 五个挂点

环线程读包，遇到这五类就甩给渲染器：

`EmitPaquete` / `EmitDibujo` / `EmitResolve` / `EmitTransferencia` / `EmitSwap`

### 3.2 完全不做 EDRAM

360 的 EDRAM 有 10 MB、按 80×16 的瓦片组织，超了就 tile-resolve 回主存。
原生路径**不模拟它**：

- 渲染目标 = 普通 Vulkan image，尺寸按 pitch 走
- **resolve = 拷贝进纹理**
- 如果下一次绘制马上就 clear，就**两张图交换**，连拷贝都省了（"resolve without copy"）

这一步是整个性能翻倍的关键：模拟路径里 868 次/帧的渲染目标拷贝是模拟器自己的税，不是游戏的要求。

### 3.3 每次绘制要做什么

1. 从 GPU 设置副本算 pipeline
2. 两级纹理缓存查纹理（**用原始字节指纹判断有没有变**，变了才 untile；不常变的纹理检查间隔
   从每帧拉到 32 帧一次）
3. 顶点去重后按字节序翻好，进上传缓冲
4. 变了的着色器常量写进动态 uniform buffer（不是一条条读内存）
5. 只绑定变了的东西，录绘制

### 3.4 线程

| 线程 | 职责 |
|---|---|
| 游戏线程 | 跑重编译出来的代码（CPU 主要负担） |
| 环线程 | 读 PM4、录 Vulkan 命令（**整帧耗时基本等于它转一圈**） |
| 顶点拷贝 | 顶点/索引转换 |
| 呈现 | present |

三槽并行：每帧录进三槽之一，各有自己的命令缓冲、fence、64 MB 上传缓冲、读回缓冲。
CPU 录下一帧时 GPU 在画当前帧。

## 4. resolve 与"别名"模型（2K13 最麻烦的部分）

游戏大量复用 guest 内存：同一段物理地址，这一刻是渲染目标，下一刻是纹理，再过一会儿又变成
另一张渲染目标。渲染器给每张"resuelta"（已 resolve 的图）维护一份**身份**（地址+宽高+格式），
而游戏经常用**不同的格式/尺寸去 fetch 同一段内存**。

这就产生了本项目一半以上的 bug：

| 现象 | 机制 |
|---|---|
| 头像框里叠着别队队徽 | fetch 声明格式 A，内存里实际是格式 B 的内容，身份缓存没刷新 |
| 比赛里地板一半黑 | fetch 落在别人的 resolve 里，取样坐标/裁剪错位 |
| 记分牌消失 | 呈现时选错了缓冲，选中的是"被下游读"的中间图 |
| 预热 MV 两个画面 | 兜底逻辑把中间图当 Swap 呈现，与游戏自己画的那张交替 |

对应补丁：C23（落在 resolve 内的纹理）、C30/C45（清除方框只清深度不清颜色）、C46（选呈现目标时
跳过被采样的图）、C47（CPU 重写 resolve 内存）、C48（兜底要先看 Swap 有没有真收到像素）。
详见 [03-修复账本.md](03-修复账本.md)。

## 5. 内存账本

guest 物理堆 = **512 MB**，是这类游戏最容易炸的地方。

- 开机常驻 arena：`0xA2B20000 + 0x1d180000`（465 MB）
- 两笔 12 MB 的 PHYSPAD（64 MB 对齐申请的回退）
- 崩溃链：4 KB 分配风暴 → `Heap exhausted!` @ `xmemory.cpp:1675` → SD 日志洪水 + nv IPC 风暴
  → 全线程卡死在 `binderCreate+0x18`

所以有：

- **C39**：日志限速 + `[C39] monton fisico` 账本（每 60 秒打印活/空闲/块数）
- **C39b**：逐出 bases 日志
- **C37**：`resueltas_` 的 LRU，上限 96（内存泄漏的真凶，真机验证后稳定 95–96）

**有一个反例要记住（C41b）**：为了省 16 MB 把 64 MB 对齐块的保险垫撤了，结果游戏越界写踩坏数据，
预热 MV 卡死在 `PM4_IM_LOAD`。**省内存不能省保险垫。**

## 6. 着色器库

原生渲染器需要一个包：`NBA2K13_shaders.nfsp`（本项目 v10 = 259,964,744 B，7,380 个着色器）。

- 查库键：**原始容器字节的 XXH3 指纹**（不是微码，因为到环上时微码已经被 D3D 改过）
- 每个着色器附带元数据：顶点元素（DeclUsage）、sampler 类型、是否 shadow map、输出、kill 位
- 容器是 **2008 版**（`0x102A1100`），与 NFS 的 2005 版布局不同，解析代码在
  `app/src/nativo/nba2k13_shader_library.cpp`
- 硬限制：**256 个寄存器**，超了直接 `DEVICE_LOST`

## 7. 线程与同步的坑

| 问题 | 现象 | 做法 |
|---|---|---|
| futex 忙等 | CPU 100%，帧不走 | C36：定点唤醒（`RegistroEspera`），真机确认 |
| 环形死锁 | GPU 利用率 0、画面定格 | C43 看门狗（检测环里 `leido` 不前进） |
| 自愈反而更糟 | 卡包被丢弃后数据错位 | C44 自愈**已关闭**（丢掉的是合法半截包） |
| 取消类型 assert | 随机崩 | C40 |

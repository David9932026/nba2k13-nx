## 卡点 1 · 技术统计页的球员头像碎片 🔴 未解

**现象**：技术统计页里，球员头像框被别的东西占满 —— 队徽碎片、竖条纹、灰白黑糊块、或者别的球员的片段。
（选项菜单里的同一类问题已经由 C45 修好，真机确认；统计页这一处不一样。）

**已经排除**：

| 试过 | 结果 |
|---|---|
| C42 别名刷新 | 真机 0 触发，无效 |
| C47 CPU 重写 resolve 内存 | 真机触发 3 次（`0FB21000 1024x1024` 等），画面无变化 |
| C49 原始字节 dump | 设的格式（8888）+ 尺寸（128/256）不对，抓了 0 个文件 |

**现有证据**：

- `C23 dentro` 大量出现：256×256 格式 6 的纹理落在 `0FB21000 1024×1024` 这块 resolve 内部，
  判定为 `no cabe: memoria guest` 或 `se muestrea de la resuelta`。
- `C13 cuadro lleno opaco sin textura: PS F0412447847F6D27 en 1040x1040` —— 1040 那头像目标上有
  "全屏不透明、但没有纹理"的绘制。
- **赛前首发卡那 10 张 150×300 不是统计页的头像**：PC 上把它们导出看是干净的，说明那条路径没问题，
  统计页走的是另一条。

**当前最像的解释**（假设，未验证）：
统计页头像走的是 `C23` 那条分支 —— 文字/图标纹理落在别人的 resolve 里，格式对不上，于是"改从 guest 内存读"。
但 stats 头像可能是**压缩格式**（DXT1/DXT5/DXN，日志里见过 formato 59 疑似 `k_DXT5A`），
resolve 永远产不出这些格式，于是渲染器把一段"CPU 刚写进去的别的图"当像素读 → 碎片看起来像别的东西。

**下一步（怎么打）**：
1. 给 `C23` 的"格式不同 → 从 guest 内存读"分支加一条**限速日志**，把格式、基地址、落点、读到的前 16 字节打出来。
2. 真机进统计页，让日志说出那几张头像的真实格式和地址。
3. 若是压缩格式：**在 CPU 侧解码**（Xenos 的 DXT/DXN/CTX1 解码表在 `sdk` 里有），或者把这块判给 CPU 直接生成一张
   对应格式的纹理，而不是按 8888 去读 guest 内存。
4. 判据：统计页 10 张头像的 PNG 导出，逐像素统计"非零像素占比"和"边缘梯度"，与干净单人肖像比。

## 卡点 2 · 部分场馆的木地板整片发黑 🔴 未定位

**现象**：某些场馆里，球场木地板不是木纹，是一大块不规则的纯黑；**三秒区刷的漆还在**，但木纹没了，
球场边线画到黑块边缘就断掉。边线断掉这点很关键 —— 说明不是"上面盖了东西"，是**地板本身的绘制错了**。

**已经排除**（全部在 PC 上做的 A/B，逐像素统计黑像素占比）：

| 关掉什么 | 结果 |
|---|---|
| C23 子区域取样 | 黑地板还在 |
| C18 只取左上角（`recortar_resueltas`） | 黑地板还在 |
| mipmaps | 黑地板还在，而且更糟（黑帧数 10 → 25） |
| n982（唯一读整场深度图的光照步骤） | 黑地板还在 |
| 阴影贴图缩放 70%（Switch 设的值） | PC 上 70/100 各跑一轮，**无差别** |

**已经确认的**：

- **PC 上也复现**，与平台无关（活塞 vs 勇士在甲骨文球馆，木地板整片黑，三秒区颜色还在）。
  → 不是 Switch 的内存/性能问题，是渲染器本身的 bug。
- `n982` 在 Switch 日志里 79 次都只采样 `05822000`（合成深度，1280×720 格式 22）。它**不是地板**。
- 地板光着色器只采样合成深度这一条（历史结论，475 次采样全部指向 `05822000`）。
- 部分场馆纹理是从 1024×1024 的 resolve 里取样的（`0F5D0000`/`0FB21000`/`10072000`/`105AD000`），
  其中含 DXT1/DXT5/DXN 压缩格式和 formato 59 —— **resolve 不可能产出这些格式**。

**下一步（怎么打）**：
1. **先认出"谁画地板"**：用 `nba2k13_nativo_diag_omitir_ps` 按 PS 指纹二分跳过，每次跑一场演示，
   用 `tools/suelo_tot.py` 统计黑像素占比（**不要用眼睛判，也不要用视觉模型判**）。
   跳过哪个之后木地板整片消失 = 找到它。
2. 找到之后，看它采样的纹理：基地址、声明格式、是否落在某张 resolve 内。
3. 候选修法（暂命名 C50）：**压缩格式 / 非 8888 的 fetch 落在 resolve 内时，把这块区域判给 CPU，
   从 guest 内存按它自己的格式解码，而不是按 resolve 的格式去读。**

**注意**：PC 演示模式每次随机球队和场馆，逐帧 A/B 靠不住（两轮之间画面差异 50–80%，不是同一帧）。
统计必须**跨整段聚合**，看"出现大片黑的帧数"，不是看某一帧。

## 卡点 3 · 预热 MV / 特写仍然是两层画面 🟠 部分修复

**现象**：赛前预热 MV 播的时候，画面里同时有两个会动的画面 —— 一个清楚、一个模糊/虚，占的位置不同。

**已经做了什么**（C48，PC 验证）：兜底逻辑（C5g）以前会把"场景中间图"当画面呈现，而游戏自己在往真正的
Swap 上画，两者交替 → 看着像两层。C48 让兜底先看这一发送里 Swap 有没有绘制，有就呈现 Swap 自己。

**结果**：PC 上接缝帧从 10 张降到 2 张；但**真机上两层还在**（用户确认）。
日志侧 C48 每 10 秒都在起作用（`se presenta el propio Swap`，数百次），C5g 只剩 1 次。
→ **说明还有另一条路径在产生"两个画面"**，不是选错缓冲。

**现有线索**：
- 剩下的那 2 张接缝帧发生在换场过程中，C48 没触发、C5g 也是 0 —— 属于另一条路径。
- 那个残留的接缝形态是"左上象限变成模糊/去饱和的一块矩形"：
  典型的**半分辨率层（640×360）被整屏放大后只占 1/4**，也就是 UV 或裁剪算错。

**下一步**：
1. 需要一张真机照片：**模糊那层占画面哪一块**（左上 1/4？整屏？下半？）。这一条只有用户能提供。
2. 按照片形状去查对应尺寸的目标：`18C3D000 640×360`、`1A353000 640×360`（半分辨率层）与
   `640×720` 那一档 pitch，看它们的裁剪窗口与 UV 来源。
3. 判据：`tools/borde48.py` 的接缝检测，接缝帧数降到 0。

## 卡点 4 · 菜单文字被裁 🟡 小问题，有明确方向

**现象**：菜单里的字被切掉一部分，例如 `THUNDER` 显示成 `UNDER`。

**方向**：文本走图集（atlas），取样矩形超出图集边界就会被裁。嫌疑在
`recortar_resueltas` / C18 的裁剪路径 —— 它对"声明尺寸小于 resolve 的纹理"会做裁剪，
如果字体图集正好落在某张 resolve 里就会被波及。

**下一步**：打开 `C18 tamano` 日志，找声明的尺寸与字体图集匹配的那条；确认它的裁剪矩形是否越界。

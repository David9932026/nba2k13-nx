# 2K13 原生渲染器：可行性判断与计划

来源：`rex\nfsmw-nx-main\docs\`（`native-renderer.md`、`performance-history.md`、`porting-another-game.md`、
`measuring.md`、`platform-notes.md`）。这套 SDK 就是我们现在用的这套，所以下面的事实不是传闻，是同一份代码里写的。

## 为什么必须走这条路

他们自己（同一台 Switch、同一套 SDK、同一款 NVK 驱动）的实测：

| 场景 | 模拟 Xenos | 关掉 resolve | 关掉全部 GPU 工作 |
|---|---|---|---|
| 标题画面 | 10 fps | 26.7 fps | 58.6 fps |
| 菜单（约 800 次绘制） | 3.3 fps | | 14 fps |
| 比赛 | 2.0–2.2 fps | | 2.1 fps |

- 模拟的代价是 **每次绘制约 80 µs CPU**（我们菜单 973 次绘制 → 78 ms/帧，理论天花板 12 fps；实测更低是因为
  还有 GPU 通道堵塞和内存压力）。
- 一次 resolve 在 GPU 上要 3–4 ms。我们每帧 19 次 resolve → 57–76 ms，光这一项就没有预算了。
- 比赛里把 GPU 工作全关掉，帧数一点不涨 → 瓶颈在 CPU，不在 GPU。
- 他们砍了两天只到 3.7 fps，离 30 太远，才决定重写。

**结论：模拟路线在这类游戏上没有 30 帧的可能，调参不可能到达。** 这跟我们的实测完全对得上。

## 原生渲染器的做法（他们总结的骨架）

1. 游戏自己的 Direct3D 完全照常跑，一个函数都不替换。
2. 只读它写给 GPU 的 **PM4 命令环**：设置、绘制、拷贝、帧结束（Swap）。
3. **完全不模拟 EDRAM**。渲染目标变成普通 Vulkan image，resolve 变成拷贝进纹理；下一次就 clear 的可以
   直接交换两张图（"resolve without copy"）。
4. 几个钩子补命令环里没有的信息：哪个着色器是哪个（着色器到达环里时已经被 D3D 改过，认不出微码）、
   以及 `WAIT_REG_MEM` / `SCRATCH_REG` 的握手（游戏等 GPU 写一个值，不写就一秒内卡死）。
5. 线程分工：游戏线程 / **环线程**（记录 Vulkan 命令，整帧的耗时基本等于它一圈的时间）/ 顶点拷贝线程 / 呈现。
6. 三槽并行：每帧录进三个槽之一，各有自己的命令缓冲、fence、64 MB 上传缓冲、读回缓冲。CPU 录下一帧时 GPU
   在画当前帧，只在槽还忙时才等。

## 每次绘制要做什么（这是性能的核心）

1. 从自己的 GPU 设置副本里算出要用哪条 pipeline；
2. 两级纹理缓存里找纹理（**用原始字节的指纹判断有没有变**，变了才 untile；不常变的纹理检查间隔越拉越长，
   到 32 帧一次。PC 上把纹理开销从 66 µs/绘制 降到 4.2 µs/绘制）；
3. 顶点去重后按字节序翻好转进上传缓冲；
4. 变了的着色器常量写进一个动态 uniform buffer（不是一条条读内存）；
5. 只绑定变了的东西，记录绘制。

他们的结果：原生渲染器在 PC 上**两天**就能画出影片、菜单、HUD 和完整比赛，代价 **1.5–1.8 µs/绘制**。
主机上首次原生构建 = 16.1 fps（中位），之后三步调到 30+。

## 我们的起点比他们当时好

- 着色器翻译（Xenos 微码 → SPIR-V）已经在我们这套里跑通了，原生渲染器可以复用，不用重写。
- 我们已经知道 2K13 的绘制流长什么样（`[FRAMESIG]` / `[SEQDUMP]` 那批数据）：菜单 973 次绘制、

- 内存分类账、栈采样、GPU 命令环探针都是现成的。

### A/B 实测：关掉渲染目标传输（`ab.txt` = 2）— 2026-10-30 21:35

`kModes` 里编号 2 = `sin transferencias`，关掉的是传输绘制（`render_target_cache.cpp:5415`）
和深度回写 dispatch（L4789）。报告头 `modo: sin transferencias` 确认已生效。

**结论：不是杠杆，而且会破坏状态。**

| 场景 | 绘制/帧 | 传输 | fps | 帧长 |
|---|---|---|---|---|
| 加载画面 | 4 | 关 | **29.6 / 30.7 / 30.1** | ≤32.6 ms |
| 主菜单 | 920 | 关 | 2.1 → 1.3 → 0.9 → 0.8 → 0.6 → 0.5 → **0.4**（逐段下降） | 476 → 2500 ms |
| 主菜单（基线） | 938 | 开 | 0.64 | 1562 ms |

1. **那个 30 fps 是 4 次绘制的加载画面**，不是菜单。而且它是被卡住的：`cola de la ventana 30.7`、
   `CPU total 196%`、`svcSleepThread 5105 ms/s`——线程大量在睡，不是在算。
2. **满场景关掉传输后更慢**（0.4 vs 0.64），而且 20 秒内从 2.1 落到 0.4，同时 `trans llamadas` 从 933 涨到 989
   而绘制数不变——跳过的传输在缓存里越积越多，状态被拖坏。所以这个模式的数字后面一半是脏的。
3. 由干净的两个点推算边际成本：162 绘制 → 260 绘制，帧长 49.8 → 112 ms，**≈0.63 ms/绘制**；
   260 → 920 绘制，112 → 476 ms，**≈0.55 ms/绘制**。两者一致。

**要多少才够：** 920 次绘制要跑进 33 ms，需要 **36 µs/绘制**。原生渲染器是 1.5–1.8 µs，**余量 20 倍**。
模拟路径现在是 600 µs，差 17 倍。只算绘制这一项，模拟路线在菜单上就永远到不了 30。

**所以 B（查 69 次传输的原因）不做了。** 省下来的 381 次传输绘制顶多值 0.2 秒，而瓶颈是 0.6 ms × 920。

**两条 P3 的硬结论：**
1. **932 次渲染目标拷贝是模拟器自己的税**，不是游戏的要求——渲染目标在两张图之间来回切，每次切都整块抄一遍。
   原生渲染器里这一步不存在（RT 就是普通 image，resolve 变拷贝、下一次就 clear 的直接换图）。
2. **不能再把这套拷贝语义带进原生路径**，否则就算绘制降到 1.7 ms，光拷贝还是 0.6 秒一帧。

**P2 最小可画**
- 复用现有 SPIR-V 翻译，把一帧里的绘制用 Vulkan 直接录出来；先不追求正确（贴图错、缺 pass 都可以），
  只要出画面、帧数有意义。

**P3 补齐**
- 渲染目标当普通 image、resolve 变拷贝、纹理两级缓存 + 指纹、顶点拷贝线程、三槽并行、动态 uniform buffer。
- 这一步之后才谈得上"能玩"。

**P4 调优（他们记录里最花时间的部分）**
- 跳过不可见绘制、合并重复 clear、语义钩子重写游戏侧最慢的函数（每个都有"双重运行 + 比对"的护栏）、
  pipeline 预编译缓存、ZCULL、动态分辨率。

## 老实说的预期

- **能跑**：P0–P2 是两三天级的工作量（他们有两天出完整渲染器的记录，我们复用着色器翻译）。
- **稳 30**：P3–P4 是长的，他们从 16.1 fps 到 30+ 走了 7 步。2K13 比 NFS 重（菜单 973 次绘制），
  能不能到 30 要看补完 P3 之后的天花板。
- 这条路上**不该再指望模拟路线**。模拟这边我只会再做"验证性"的改动（比如 present 修复），
  不再做无休止的调参。

### 唯一的拦路石

```
[nativo] C5a: biblioteca de shaders no disponible (…\win-vk\NBA2K13_shaders.nfsp): No se pudo abrir el paquete
```

原生渲染器靠**原始容器**（header + 常量表 + 定义 + 微码）的 XXH3 指纹查库，N2a 采到的是**微码 + SPIR-V**，两者对不上：

- `natsh::Shader{original, spirv, huella=XXH3(original), vertices}`，`EmpaquetarShaders` 写这个包；
- `ShadersNativos` 还要每个着色器的元数据：顶点元素（DeclUsage）、sampler（D3DX 类型 / 是否 shadow map）、`salidas`、`kills`、`sombra_minimo`；
- 这些元数据都从**容器**里解析（XenosRecomp 的 `shader.h`）。

所以 N2d 要做的：采集端补一份原始容器字节（或在 `D:\xox360_extract` 里按 `10 2A 0E 00/01` 扫容器，跟 NFS 一样），再用 XenosRecomp 的解析代码生成元数据，最后用 `EmpaquetarShaders` 打成 `NBA2K13_shaders.nfsp`。

## 16 GB 解析包通不通用？——N2d 实测（2026-10-30 23:50）

结论：**数据通、元数据不通，代码要改两处**。改完着色器库能加载，但绘制还没进来。

### 通的部分

- 在 `D:\xox360_extract`（11,822 个文件 / 16,401 MiB）里扫出 **84,078 个候选容器**，去重后 **7,338 个**（910 VS / 6,428 PS）；`D:\xox360\00007000\...`（8 GB 原始包）里一个是 **0** —— 原始包是压缩的，只能用解析包，这点用户判断对了。
- 同位图（三张 1280×720 面、`035F0000 / 03988000 / 05822000`）和顶点、索引数据都在解析包里，能直接对上。

### 不通的部分（这就是"不通用"的地方）

NFS 用 **2005 版容器**（签名 `0x102A0E00`），2K13 用 **2008 版**（`0x102A1100`）。差别：

| | NFS / 我们的移植原版 | 2K13 |
|---|---|---|
| 签名 | `0x102A0E00` | `0x102A1100` |
| 头长度 | 24 字节（def@12 / ct@16 / sh@20） | **36 字节**（ct@16 / def@20 / **sh@24**） |
| 微码位置 | 整个物理区 | `virtualSize + shader->physicalOffset`，长度 `shader->size` |
| 物理区大小 | 12 的倍数 | 任意 |
| VS 元素表 | 转换后 `cab+40` | `cab+36` |

改了三处：
1. `src\nativo\nba2k13_shader_library.cpp` 的 `Validar`：签名只比高 16 位（`0x102A0000`，与 XenosRecomp 一致），去掉"物理区必须是 12 的倍数"。
2. `src\nativo\nba2k13_nativo_shaders.cpp` 的 `Leer`：按 2008 布局读（ct@16 / sh@24），微码从 `physicalOffset/size` 取，VS 元素表 `cab+36`。
3. 打包工具 `tools\shaders-2k13\empaquetar_2k13.cpp`（新）：扫容器 → 与 `.nflib` 的微码配对 → 写 `EmpaquetarShaders` 包。

### 配对规则（关键发现）

- **PS 精确匹配 119/134**：像素着色器到环上原样不动，XXH3 直接命中。
- **VS 一个都精确匹配不上**：D3D 会改写 fetch。NFS 的掩码 `{0x0007FFFF, 0x80000FFF, 0x80000000}` 在 2K13 上**不够**（2K13 改动更多位，例如字 1 从 `0x00000688` 变成 `0x402034C1`）。
- 换成**位置规则**后成功：所有差异都落在容器声明的 fetch 指令那三字里（实测 9 处差异全部在指令 4/5/6/7 的三字区间内）。按这条规则配上 **107 个 VS**（16 个有歧义）。
- 同一个容器可能有多个翻译（同一 VS 的不同 fetch 补丁）：包格式一个容器只允许一条，27 个冲突只留第一条。

产物：**`NBA2K13_shaders.nfsp` 17,306,684 B（80 VS + 119 PS）**，共 199/251。

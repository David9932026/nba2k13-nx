只读分析。目标：把 nfsmw-nx 里挂钩的那批 XDK Direct3D 库函数，在 2K13 的静态重编译代码里定位出来。

## 2. 逐条证据

### 2.1 `825A3A40` ↔ `82CC1560`（着色器补丁 pass）

两边**逐条同构**（只差寄存器分配和字段偏移）：

```
NFS                             2K13
lbz  r11,0(r3)                  lbz  r11,8(r3)
clrlwi r11,r11,29               clrlwi r11,r11,29
cmplwi cr6,r11,7 / beq          cmplwi cr6,r11,7 / beq          <- 已编译/空着色器直接返回
lwz  r10,16(r3)                 lwz  r10,20(r3)
rlwinm. r11,r10,0,13,13 / bne   rlwinm. r11,r11,0,13,13 / bne   <- "不补丁" 位
...
addi r11,r11,10                 addi r11,r11,9                  <- 头部长度差 1 dword
rlwinm r11,r11,2,0,29 / add r31,r11,r3
...
lbzx r11,3(r31) / cmplw / bge
bl 0x825A3930                   bl 0x82CC13D8
...
xor / rlwinm. 0,20,23 / beq
bl 0x825A39C0                   bl 0x82CC14A8
...
lwz r11,0(r24) / rlwimi r11,r25,20,8,11 / stw r11,0(r24)     <- 尾部完全一致
```

这是「把常量/字面量补丁进着色器微码」的那一步。

### 2.2 `825A3B70` ↔ `82CC16B0`（微码上载到命令环）— 任务项 1a

**是**「把着色器微码拷进命令环」。逐条对应：

```
NFS                                         2K13
lwz  r28,600(r26)         微码 dword 数      lwz  r27,876(r11)
addi r4,r29,3 / bl 82596318  申请环空间     addi r4,r28,5 / bl 82CAF250
lis -16384 / ori 11008 (0xC0002B00)          lis -16384 / ori 15104 (0xC0003B00)  <- 新增
rlwimi r10,r11,16,2,15     count=(n+1)      li r10,256                            <- 新增 dword
stwu r10 / stwu r11 / stwu r9                stwu / stwu / stwu 0xC0002B00 / stwu 0 / stwu n
lwz  r11,40(r26)           GPU 指针          lwz r10,32(r31) + lwz r11,872(sub)    <- 指针改成 base+offset
rlwinm 12,20,31 / clrlwi 3 / addi 512 / rlwinm 0,19,19 / add r / addis -16384       <- 完全一致（GPU→环偏移换算）
sync
bl 826BE130  (memcpy)                        bl 82CC2B50  (memcpy)
bl 825A2938  (清尾)                          bl 82CB52A8  (清尾)
cmpwi r24,0 / beq                            cmpwi r25,0 / beq
bl 825A3A40  (补丁 pass)                      bl 82CC1560  (补丁 pass)
cntlzw/xori -> flag                          addic/subfe -> flag
lbz/stb r11,10433(r31)  bit0                 lbz/stb r10,11070(r30)  bit7          <- 脏标记位不同
bl 825A3350  (fetch 重建)                     bl 82CC0DB0  (fetch 重建)

2K13 版比 NFS 版**多写了 2 个 dword 的前导包**（`0xC0003B00|count` + `0x100`），且微码指针的取值方式从「直接读字段」变成「读一个基准值 + 偏移」。移植时这两点都要跟着改。

### 2.3 `825A3350` ↔ `82CC0DB0`（顶点抓取描述符构建/排序）— 任务项 1c

**是 fetch 补丁器**，但对应的是**整个 `825A3350` 函数**，不是 `825A2FB8`。

后段（NFS `825A3674` 起 / 2K13 `82CC1108` 起）是逐条一致的冒泡排序：

```
NFS 825A367C  lwz r11,0(r27) / rlwinm. r11,r11,0,10,11 / bne     <- 跳过 marker 项
NFS 825A36A8  bge cr6,0x825a38e0
2K13 82CC1114 同；82CC110C 同 bge
...
NFS 825A37DC.. 三次 lwz/stw 交换 12 字节项
2K13 82CC1274.. 同样三次 lwz/stw
NFS 825A38B0  rlwimi r8,r10,27,2,4 / stw r8,0(r7)
NFS 825A38BC  lwz r10,4(r11) / oris r10,r10,16384 / stw r10,4(r11)
2K13 82CC1368 / 82CC1370..1378 完全一致
NFS 825A38DC  b 0x825a3674（回到外层）
2K13 82CC138C  b 0x82cc1108
NFS 825A38F0.. clrlwi r9,r9,20 / mulli r9,9,12 / add r9,r9,r5 / 三次 stw  回写
2K13 82CC1398.. clrlwi r11,r11,20 / mulli r11,11,12 / add r3,r11,r23 / bl memcpy(12)
```

前段是「把声明项翻成 12 字节抓取记录」：读属性类型/实例/步长/偏移，用 `0x8221CB88`（NFS 是 `-32250:516`）的 16 位掩码表做位序还原，`oris …,14` 写抓取类型，`0x01560056` 做魔数哈希。

**重要更正**：`82CC0DB0` **不**从 `+13072/+13068/+12240` 读。它读的是：
- `device + 68 + 416*idx`（每槽 416 字节描述符数组）
- `device[896 + 8*idx] + device`（偏移表）再 `+872`（当前声明子结构），字段 `+24`/`+28`
- 入参 `r5+52`（12 字节项数组）、`r5+24`（项数）、`r6`（属性→字节类型查找表基址）

`+13072/+13068/+12240` 是**别人**读的：`82CAB0A8`(SetVertexShader)/`82CAAEA0`(SetPixelShader)/`82CC19F8`(Flush)。这三个偏移是设备上「当前 VS / 当前 PS / 当前声明」的槽位。

### 2.4 `82CC18B8`（顶点声明脏检查）— 任务项 1b

**它确实调 fetch 补丁器**（`bl 0x82CC0DB0` at `82CC197C`，返回 `82CC1980`）。自身逻辑：

```
mulli r11,r6,416 / add r28,r11,r4        <- 取 416 字节槽
lwz r11,48(r5) / lwz r10,40(r28) / cmplw <- 版本戳比较
ld  r9,12912(r3) / ld r8,12904(r3)       <- 设备上的 64 位代戳
ld  r10,56(r28) / ld r11,48(r28) / ld r6,32(r5) / ld r9,40(r5)
xor/and/or / cmpldi                      <- 掩码化比较，未变则直接返回 1
lwz r11,64(r28) / lwz r10,11024(r30) / lwz r9,11036(r30)   <- 环上还有未完成帧 → li r3,0 返回失败
addi r11,r7,112 / rlwinm 3,0,28 / lwzx ... +872 / lwz r10,32(r4) / add r4,...
bl 82CC0DB0 (r3=r4基, r4=目标, r5=信息, r6=device+12904, r7=槽号)
lwarx/stwcx. 全局计数器自增（0x84217F50 家族）
stw 新戳 → 40(r28); std 设备戳 → 48(r28)/56(r28)
std 设备戳 → 12264(device)/12272(device)
```

NFS 侧这段在 `825A3E88` 里是**内联**的（`825A3E88` 一次调 `825A3B70`、一次直接调 `825A3350`），2K13 把它提到了独立函数。所以 NFS 没有一一对应的独立函数——移植时要么在 `825A3E88` 里找内联块，要么直接照 2K13 拆分。

### 2.5 环等待 / 读指针偏移 — 任务项 2

**找到**：NFS `82597A28` ↔ 2K13 `82CADC38`（51 条，指令级同构）：

```
NFS 82597A28                                2K13 82CADC38
lwz r9,10384(r31)   环控制块指针            lwz r11,11024(r3)     <- device+0x2B10
lwz r11,10396(r31)  写偏移                  lwz r10,11036(r3)     <- device+0x2B1C
subf r8,r10,r11                             subf r9,r4,r10
lwz r9,0(r9)        **GPU 读指针**          lwz r11,0(r11)        **GPU 读指针**
subf r9,r9,r11 / cmplw / bge                subf r11,r11,r10 / cmplw / bge
...
lwz r11,13520(r31)  idle/lost 标志          lwz r11,13600(r3)
bl 82597600         不够就先 Present/Flush    bl 82CAF018
...
bl 825A60B0         自旋等待体              bl 82CA2BB0
```

**答案：2K13 的读指针在 `[[device + 0x2B10]]`（= `*(u32*)device[11024]`），写偏移在 `device + 0x2B1C`（11036）。**
NFS 对应是 `[[device + 0x2890]]`（10384）/ `device + 0x289C`（10396）。

附带：2K13 的等待函数比 NFS 多一个 `r7` 参数（`clrlwi. r11,r7,24` 做模式判断），且不再通过 `r13` TLS 取当前线程（NFS 用 `lwz r8,256(r13); lwz r8,88(r8)`）。另外 NFS 的 compare 直接拿 `r4`/`[r30]` 当目标值，2K13 直接用寄存器 `r4`。

### 2.7 `8259C300` ↔ `82CAB780`（着色器对象初始化）

```

## 3. 设备结构差异（移植时要改的地方）

### 3.1 设备（D3DDevice）字段

| 用途 | NFS 偏移 | 2K13 偏移 | 备注 |
|---|---|---|---|

## 4. 「不要的」——2K13 里可以整块删掉的逻辑

### 4.1 遮挡查询（整套删掉）

**结论：2K13 不用遮挡查询。** 双向验证：

1. 标记 `0xFFFFFEED`（`li rX,-275`）：
   - NFS：**只有 1 处** — `8258FBA8` @ `8258FBDC`（`li r11,-275`），然后 `mr r9/r8/r7/r6` 连写 4 个 dword。
   - 2K13：**0 处**。全库 `li <reg>,-275`、`lis <reg>,-275` 均为 0（唯一两处 `,-275$` 命中是 `0x82DC2CF0` 的 `lis r11,-275` 与 `0x82DC3388`，前者是存档/授权校验里的 `0xFEED0004` 魔数，与查询无关）。
2. 查询用的两个 PM4 包 `0xC0004600`（`ori …,17920`）与 `0xC0015A00`（`lis -16383; ori …,23040`）：
   - NFS：**`8258FBA8` 是唯一同时具备这两者的函数**。
   - 2K13：`17920` 命中 11 个函数、`23040` 命中 10 个函数，**交集为空**。没有任何函数同时会发这两个包。
3. 2K13 也没有 `device+20460` 这个「查询链表头」字段（NFS 的 `8258F810` 从 `addi r31,r3,20460` 起步遍历链表分配 16 字节/4096 字节节点）。

**移植影响**：NFS 里这三块可以整块不要 —
- `8258F810` Issue(BEGIN)
- `8258EA28` Issue(END)
- `8258F998` GetData
- `8258FBA8` 查询分发器
- 以及 `8258FD30`（159 条，4 处 `-275`，查询 flush）

> 注：任务书建议的「搜 `D3DDevice_BeginQuery` / `EndQuery` / `GetQueryData` 导入名」这条路**不可用**。rexglue 生成代码不带任何 API 名，NFS 侧和 2K13 侧搜这些关键字都是 **0 命中**（`manifest` 里也没有符号表）。所以只能靠常量/包/结构反推，上面的三条依据就是这么来的。

如果 2K13 侧确实需要遮挡剔除（原作可能用别的机制，比如 CPU 端视锥/区间遮挡），那要重新看 2K13 自己的剔除路径，不能从 NFS 搬。

### 4.2 `0xC0025801` event write

NFS 的 `82597930`（`EmitWriteEvent(device, destGPUAddr, value)`，包 `0xC0025801`）在 2K13 里**没有对应**。2K13 只有 `0xC0025800`。所以「vblank 计数 + 单发 event write」这条钩子不能 1:1 翻译（见 §5.1）。

## 5. 未解决 / 部分解决

### 5.1 vblank 计数（任务项 3）— 部分解决

- NFS 侧**已精确定位**：`82597930`（28 条）
  ```
  lwz r11,0(r31) / lwz r10,8(r31) / cmplw / ble   ; 环满先 flush
  lis -16382 / ori 22529                          ; 0xC0025801
  地址换算 / ori r10,r10,2
  stwu header / stwu 3 / stwu addr / stwu value
  stw r11,0(r31)                                  ; 更新写指针
  ```
  这是 `EmitEventWrite(device, destGPUAddr, value)`，`3` 是 event 类型，`value` 由调用者给。
- 2K13 侧：**只有 `0xC0025800`**（12 处），没有 `0xC0025801`。姊妹函数 `82597328` ↔ `82CAE588` 已按指令级对上（高）。
- 任务书给的线索「`0x82CAE6C8–0x82CB5908` 一带多个函数出现 `0x0BADF00D`」已验证：`0x0BADF00D` 出现在 `82CAE6C8`(253)、`82CAF398`(242)、`82CB50B0`(158)、`82CB5908`(559)、`82DA2470`(228)、`82EEA460`(23)。NFS 侧对应有 11 个函数（`82593670`/`82593998`/`82593DA8`/`82593FE8`/`82594238`/`825944F8`/`82597BD8`/`82597CF8`/`82598580`/`82598668`/`825AD1E8`）。
- **建议的移植做法**：不要去找「NFS 82597930 的 2K13 翻译」，而是把 vblank 钩子重新锚定到 2K13 自己的 `0x0BADF00D` 簇（优先 `82CAE6C8`，它是该簇首个函数；`82CAE588` 已确认是 swap 提交块）。NFS 那套「单独发 0xC0025801 递增计数器」在 2K13 里被合并进了 event-write + fence 提交路径。

### 5.2 `8259BF68`（任务项 5b）— 未找到

- `8259BF68` 是一条 `blr`，属于 `8259BF40`（19 条）这个小访问器：
  ```
  lwz r11,72(r3) / add r11,r11,r3 / addi r11,r11,52   ; base = *(obj+72) + obj + 52
  lwz r10,16(r11) / rlwinm. r9,r10,0,12,12 / beq ->0  ; 位 0x1000
  rlwinm r10,r10,27,27,31 / addi r10,r10,8 / rlwinm r10,r10,2,0,29
  add r3,r10,r11 / blr                                 ; 返回 &数组[((field>>5)&0x1F)+8]
  ```
  即「取对象里某段数组的起始指针」。
- **`0x82CAB780` 不是它的对应**。`82CAB780`（62 条）是「着色器对象初始化」：`li r5,872; li r4,0; bl memset`，然后遍历 `r31+896` 偏移表把 `r31+40+416*i` 的每槽描述符重置、把 12 字节子数组从 `[off+872]+32` 拷出来、写 `-1` 哨兵。
- 2K13 里同形的访问器**没有找到**。试过：搜 `,72(r3)` 家族、搜 `rlwinm …,27,27,31` + `addi …,8`、搜全库 `rlwinm. rX,rX,0,12,12`（只有 1 个函数命中，且不是小访问器）、逐个 dump 了 `82CAB060`/`82CAB278`/`82CAB2C0`/`82CAB968`/`82CAB780` 五个近邻小函数，都不是这个形状。
- 猜测：2K13 把「`[obj+72]` 相对指针 + 位 0x1000 标志」这套换成了 §3.2 里的 `[obj+896+8*idx]` 偏移表 + `+872` 子结构，所以结构上没有一一对应。**这个钩子需要在 2K13 侧重新找挂点**。

### 5.3 `825A2FB8` — 旧结论被推翻

之前认为 `825A2FB8` 是「顶点 fetch 补丁器」并映射到 `82CC0DB0`。经核对：
- `825A2FB8` 落在 `825A2EF8`（62 条）体内（偏移 0xC0），不是函数起点。
- 真正的 fetch 补丁器是 `825A3350`（375 条）↔ `82CC0DB0`（393 条），已按指令级对上。
- 所以旧表里这一行应该改成 `825A3350 | 顶点 fetch 补丁器 | 82CC0DB0 | 高`。

### 5.4 2K13 独有但 NFS 没有的

- `82CC1808`：常量块上传（`0xC0022F00`），从 `r4+20` 遍历 `(u16 idx, u16 cnt, u32 addr)` 表项。NFS 侧没找到对应（NFS 用 `825A3C90` 那种单发 `0xC0002B00` + memcpy 的写法）。移植时如果 NFS 侧要发常量，2K13 这边可能必须走 `82CC1808` 的表格式接口。

## 6. 用到的检索方法（供复现）

所有查询都是对 `nfs.pkl` / `k13.pkl` 的指令流做正则。踩过的坑：

1. **`scan.py` 是子串匹配**，`13072` 会命中 `0x8213 072x` 这类地址。必须用 `13072[(]` 这种带走址括号的锚定写法。
2. **PowerShell 会把 `\(` 吞掉**，导致 `re.error: missing ), unterminated subpattern`。改用字符类 `[(]` 代替 `\(`。
3. **任务书里的 NFS 地址不是函数起点**。`rng.py <pkl> <start> <end>` 做线性 dump 可以直接看到「这个地址落在哪个函数里、偏移多少」。
4. 有效的定位手法（按性价比排序）：
   - 设备字段偏移：`scan.py nfs.pkl '10433[(]'` 对比 `scan.py k13.pkl '11070[(]'`，再对齐
   - PM4 包常量：`ori rX,rX,<opcode>`（如 `11008`=`0x2B00`、`15104`=`0x3B00`、`22528`=`0x5800`、`17920`=`0x4600`、`23040`=`0x5A00`、`12032`=`0x2F00`）
   - 调用关系：`q.py callers/callees`。**这一条命中率最高**——`82CC19F8` 同时调 `82CC16B0`×2 和 `82CC18B8`×2，NFS 侧 `825A3E88` 同时调 `825A3B70` 和 `825A3350`，直接锁死了整簇
   - 唯一常量：`22529`（`0xC0025801`）在 NFS 只有 1 处、2K13 只有 0 处 —— 负结论就是这么来的

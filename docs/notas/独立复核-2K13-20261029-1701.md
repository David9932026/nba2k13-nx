## 3. 旧结论复核：哪些可以确认错误

### A. “0A 读成功但全零＝IO 吞数据”证据错误

[Memory 地址转换](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/include/rex/system/xmemory.h>) 387–405：`TranslateVirtual` 查 heap/host offset；`TranslatePhysical` 固定为 physical base + `(address & 0x1FFFFFFF)`，不是虚拟地址转换。

[XFile 真正读取目的映射](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/system/xfile.cpp>) 137–165：virtual buffer 用 TranslateVirtual；physical heap 的 guest alias 先取实际 physical 地址，再 TranslatePhysical。

本轮新日志 `nba2k13_220.log` 第 67 行：`0A off=0 read=24 guest=0x7018fb60 mapped=actual=0x17018fb60 physical_heap=false head=[AA 00 B3 BF ...]`。旧探针却会读到 `0x21018fb60`，是另一块内存。

第 68 行 physical buffer 样例：guest `0xa2bc1438`，mapped `0x1a2bc1438`，XFile 实际目的 `0x202bc1438`。修复没有简单地把所有读取改成 virtual，而是匹配真实 IO 映射。

从[原始 0A](<D:/xox360/00007000/C096DB2DDEE83F64054B/0A>) 只读独立抽取 offset 0、190464、192512、192696、213986 的前 16 字节，与新诊断对应 head 一致。两轮均无 `READCERO` / `READPROBE` 条目（后者也可能因为本轮没有走相应 GUID 读取，不能据此称全 IO 都正确）。

[原盘只读 head 证据](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/recheck-independent-20261029-1652-r1/disk-0A-heads.json>)

[HostPathFile](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/filesystem/devices/host_path_file.cpp>) 708–744、746–865：direct 分支检查底层 Read bool 与实际 count；cache 分支 memcpy 并给实际 count；WriteSync 检查 Write bool。[Win32FileHandle](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/core/filesystem_win.cpp>) 121–161：ReadFile/WriteFile 失败不伪造成功字节数，成功才赋 bytes count。未在这些代码和本轮样本找到“读取成功但故意归零”的依据；这不排除未覆盖的 IO/caching 问题。

### B. “CPU 前缓冲全零＝GPU copy broken”推断不成立

[SharedMemory](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/graphics/shared_memory.cpp>) 257–272：GPU written 只触发 watches/标记 GPU 数据有效，不做通用 CPU RAM 回写。
[D3D12 SharedMemory](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/graphics/d3d12/shared_memory.cpp>) 40–75 创建独立 GPU resource；304–338 通过 upload buffer 从 CPU physical RAM 复制到 GPU，不是同一块实时共享内存。
[Resolve](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/graphics/d3d12/render_target_cache.cpp>) 1302–1320：`copied=true` 位于 deferred dispatch 之后，表示已记录 resolve 命令；无目的 extent 的路径也可置 true。不能把它当 GPU 已执行且 CPU RAM 已回写。

**本轮直接反证**：`nba2k13_221.log` 16:56:16.213 `[SURFACE] front_035F0000 / front_03988000 nonzero 0/14629`，同一时刻 16:56:16.220 GPU `PRESENTBRIGHT frame=2400 ... peak=765`。该 GPU BMP 的全像素统计 RGB 非零 **904,737 / 921,600**。CPU 探针零与 GPU 真正有画面可以同时成立。

[CPU surface probe](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/graphics/d3d12/command_processor.cpp>) 2019–2038 每隔 252 字节只看一个字节，不能证明整个 surface 的 RGBA 都为零；`image_82000000_sanity` 更把虚拟 image 地址送入 physical translator，sanity 本身无效。未修改这些旧探针，以免扩大范围。

[CaptureGuestOutput](<C:/Users/26095/cola/coding-cola/project-20261028-112651-101fe126/rex/nfsmw-nx-main/sdk/src/ui/d3d12/d3d12_presenter.cpp>) 207–347：独立 copy command list、提交、signal/await fence 后才 Map；亮度采样 560–585 只算 RGB，不算 alpha。它可能读到 consumer mailbox 的上一输出，不是未经同步的 RT/EDRAM 延时 Map。本轮不启用危险 RT/EDRAM 探针（getenv 只要存在就启用，设成字符串“0”也不安全，因此直接不继承）。

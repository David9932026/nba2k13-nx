# 01 · 研究总览

一份"为什么最后走成这条路"的记录。中间绝大部分时间是花在**排除**上的，这里把排除的过程和判据都留着，
省得后来的人重走一遍。

---

## 1. 目标与约束

- 目标：在 Switch **掌机模式**（不是底座）下跑《NBA 2K13》，稳定 30 帧，支持拆 Joy-Con 本地双人。
- 不追求画质，接受降分辨率、降阴影精度、砍后期。
- 60 帧明确放弃过：这套渲染管线在这个硬件上做不到，不是调参问题（见 §6）。

---

## 2. 排除掉的路（按时间顺序）

### 2.1 Carafe / 串流（放弃）

一开始想的是"把 PC 版渲染出来串到 Switch 上"或走 Carafe 那类方案。放弃的原因很直接：
链路依赖 PC、延迟不可控、掌机离网即废。这不是"掌机上真能跑"。

### 2.2 PC 版 + Box64/Wine 系（全失败）

试过 Box64 + WineD3D 的各种组合，五轮（省内存 / 画质 / 帧缓冲 / WineD3D / 混合）全部失败，
统一卡在 `[VAFAIL] 0xc0000017`（地址空间不足）。这条路在 4 GB 内存 + 32 位进程模型下没有出口。

### 2.3 更老的 2K / Wii / Dolphin（不可行）

- NBA 2K9 重编译：`0xc000001d @ nba2k9.exe + 0x35273`（非法指令），代码生成器对老版本编译产物支持不全。
- 2K11 / Wii 版 / Dolphin：画质与可玩性都不如 360 版，且模拟同样吃不满帧。

**结论：Xbox 360 版是这份游戏的最高版本（用户判断，实际对比也支持），值得为它做重编译。**

### 2.4 Xenia 验证（可行性预检）

先用 Xenia 在 PC 上确认 360 版能跑、画面正常，再决定投入：

- `default.xex` 8,122,368 B，Title ID `545408A2`
- Xenia 下菜单 / 比赛均正常 → 说明游戏本身没问题，剩下的是移植工程问题

## 5. 着色器库

原生渲染器靠**原始容器**的 XXH3 指纹查库，所以必须先建库。

### 5.1 容器格式差异（这是"不通用"的根源）

| | NFS（nfsmw-nx 原版） | 2K13 |
|---|---|---|
| 签名 | `0x102A0E00`（2005 版） | `0x102A1100`（2008 版） |
| 头长度 | 24 B（def@12 / ct@16 / sh@20） | **36 B**（ct@16 / def@20 / sh@24） |
| 微码位置 | 整个物理区 | `virtualSize + shader->physicalOffset`，长度 `shader->size` |
| 物理区大小 | 12 的倍数 | 任意 |
| VS 元素表 | `cab+40` | `cab+36` |

改了三处：`Validar` 只比签名高 16 位、`Leer` 按 2008 布局、打包工具
`tools/shaders-2k13/empaquetar_2k13.cpp`（新写）。

### 5.2 配对规则

- **PS 精确匹配**：像素着色器到环上原样不动，XXH3 直接命中。
- **VS 一个都精确匹配不上**：D3D 会改写 fetch 常量。按"所有差异都落在容器声明的 fetch 指令那三字里"
  这条位置规则配对才成功。

### 5.3 规模

| 阶段 | 着色器数 | 包大小 |
|---|---|---|
| 首版 | 199（80 VS + 119 PS） | 17 MB |
| v2 → v10 | 逐步补到 **7,380 个** | **259,964,744 B** |
| v10 状态 | `sin_identificar = 0`（没有认不出的了） | — |

中间踩过大坑：**XenosRecomp 的 256 寄存器上限**。开 224 个时正常，超了就 `DEVICE_LOST`。
`dxc-all-par.sh` 全量重编一轮 ok=7338。

## 6. 模拟路线为什么被判死刑

同一台机器、同一套 SDK 的实测：

| 场景 | 模拟 Xenos | 关掉 resolve | 关掉全部 GPU 工作 |
|---|---|---|---|
| 标题画面 | 10 fps | 26.7 fps | 58.6 fps |
| 菜单（约 800 次绘制） | 3.3 fps | — | 14 fps |
| 比赛 | 2.0–2.2 fps | — | 2.1 fps |

三个判决性事实：

1. **每次绘制的固定成本 ≈ 80 µs CPU**。900 次绘制 → 72 ms/帧 → 天花板 12 fps。实测更深（0.55–0.63 ms/绘制）。
2. **一次 resolve 在 GPU 上 3–4 ms**，每帧 19 次 → 57–76 ms，这一项就超了 33 ms 的预算。
3. **比赛里关掉全部 GPU 工作，帧数一点不涨** → 瓶颈在 CPU 提交侧，不是 GPU 算力。

要跑进 33 ms，900 次绘制需要 **36 µs/绘制**。原生渲染器是 1.5–1.8 µs，余量 20 倍；模拟路径 600 µs，差 17 倍。

**A/B 也试过**：关掉渲染目标传输（`kModes` 编号 2）后满场景反而更慢（0.4 vs 0.64 fps），
而且 20 秒内从 2.1 掉到 0.4 —— 跳过的传输在缓存里越积越多，状态被拖坏。那条 30 fps 的读数来自
只有 4 次绘制的加载画面，不是菜单。

## 7. 原生渲染器

**不看 D3D 调用，只看游戏写给 GPU 的 PM4 命令环。**

1. 游戏自己的 Direct3D 完全照常跑，一个函数都不替换。
2. 只读它写进命令环的东西：状态设置、绘制、拷贝、帧结束（Swap）。
3. **完全不模拟 EDRAM**。渲染目标就是普通 Vulkan image，resolve = 拷贝进纹理；
   下一次直接 clear 的可以两张图交换（"resolve without copy"）。
4. 少量钩子补命令环里没有的信息：哪个着色器是哪个、`WAIT_REG_MEM` / `SCRATCH_REG` 的握手。
5. 线程分工：游戏线程 / 环线程 / 顶点拷贝线程 / 呈现，三槽并行。

### 分阶段结果

| 阶段 | 内容 | 结果 |
|---|---|---|
| P0 | 确认 2K13 真的把 D3D 写进 PM4 环 | 是，`[CBPROBE]` / `[PHYSPAD]` 已确认 |
| P1 | 环线程只读不画 | 捕获完整性满分：`descartes=0`，938.0 vs 938.0 逐帧相等 |
| P2 | 最小可画 | PC 上出画面、菜单、HUD |
| P3 | 补齐（RT 当普通 image、纹理指纹缓存、顶点去重、三槽并行） | Switch 首次原生构建 16.1 fps（中位） |
| P4 | 调优（跳不可见绘制、合并 clear、ZCULL、动态分辨率） | 掌机模式基本稳 30 |

P1 的关键数据（决定这条路可行）：

- 菜单满场景：**938 次绘制/帧**、19 次 resolve、868 次渲染目标拷贝、155 次共享内存上传
- 绘制形状：索引数中位数 **4**（一个四边形），48 条样本里 25 条正好是 4 —— "少量大几何批 + 大量两三角形小片"
- 也就是成本全在**每次绘制的固定开销**上，而原生路径每次只要 1.5–1.8 µs

## 8. 上线后：C 系列补丁

真机跑起来之后，剩下的全是"某个画面元素不对"的案子。每个都按同一套流程走：

**日志取证 → 定位到具体绘制/目标/内存 → PC 侧复现 → 改 → 像素级前后对比 → 上卡 → 真机确认**

49 个补丁的完整账目在 [03-修复账本.md](03-修复账本.md)。这里面有两个必须记住的教训：

### 教训一：新包退化，先拿"上一个正常包"的日志做差异比对

预热 MV 放到 5 秒定格、比赛进不去，查了三轮，最后是我自己 14:24 加的 C41b（撤掉 64MB 对齐块的
16MB 保险垫）造成的：好那场的日志是 `[PHYSPAD] 64MB-aligned request widened to 0xc00000 B`，
坏的三场全是 `[PHYSPAD] C41b relleno desactivado`。撤掉保险垫 → 游戏越界写踩坏数据 → 卡在
`PM4_IM_LOAD`（着色器加载）上。

**新包出退化，第一件事是 diff 日志，不是加新补丁。**

### 教训二：视觉模型的话不能当证据

"vision 说这里是黑的"经常是错的。所有结论都走**逐像素统计**：解码 PNG → 统计非零像素、
通道均值、接缝梯度。`tools/chequea_png.py`、`borde48.py`、`abdiff.py` 就是干这个的。

它抓到过一个典型假象：探针导出的 PNG **全黑**，看着像"渲染目标没内容"，实际是
`EscribirPngDeImagen` 用 COLOR aspect 去拷 DEPTH 图 —— 无效拷贝，导出来当然全零。
